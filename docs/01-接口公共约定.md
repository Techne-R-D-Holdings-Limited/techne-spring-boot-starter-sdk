# 接口公共约定（app / web 调试用）

> 本文档说明**所有接口外壳层面**统一遵守的约定，是三份专项约定（分页、参数签名、获取第三方密钥）的"总纲"。
> - 分页出参结构 → 见《分页接口标准出参约定》
> - 参数签名怎么传 → 见《接口参数签名约定》
> - 字段级加密（三方密钥）怎么传 → 见《获取第三方密钥约定》
>
> 本文档**不重复**上述细节，只讲"任何接口都会收到的那层统一结构"。

---

## 1. 最短调用流程（前端/移动端可直接照着做）

1. 发请求时先看接口是否需要签名、是否需要字段级加密；若需要，按对应专项文档补齐。
2. 先判断 HTTP 状态码：`200` 才继续解析响应体；非 `200` 直接按网络/路径错误处理。
3. 若 HTTP 为 `200`，再看响应体里的 `code`：`200` 视为成功，其他值视为失败。
4. 成功时读取 `data`；失败时直接展示 `message`，无需继续解析业务字段。
5. 若需要排障，把 `code`、`message`、`traceId` 一并反馈给后端。

---

## 2. HTTP 状态码约定（最重要）

**所有业务成功 / 业务失败，HTTP 一律返回 `200 OK`。**

真正的处理结果**不在 HTTP 状态码里，而在响应体 `code` 字段里**（见 §3）。也就是说：

- 接口调通了（无论业务成功还是被拒）→ `HTTP 200`
- 接口根本没调通（URL 打错、路径不存在）→ `HTTP 404`（极少数情况）

> ⚠️ 唯一例外：请求路径不存在 / URL 拼错时，网关会返回 `404`。这是**客户端 URL 错误**，不是业务错误，不应按下方 `code` 逻辑处理，直接当作"地址错误"排查即可。

**客户端统一处理建议：**

1. 先看 `HTTP` 状态码：`≠ 200`（如 404）→ 按网络 / 路径错误处理，不解析 `code`。
2. `HTTP == 200` → 再读响应体 `code` 字段（见 §4 判定逻辑）。

---

## 3. 统一响应体结构（ResponseData）

任意接口（成功或失败）返回的都是同一个 JSON 结构：

```json
{
  "code": 200,
  "message": "success",
  "data": { },
  "metadata": null,
  "time": "2026-07-28T09:08:38.123Z",
  "traceId": "a1b2c3d4-5e6f-7890-abcd-ef1234567890"
}
```

| 字段 | 类型 | 说明 | 调用方怎么用 |
| --- | --- | --- | --- |
| `code` | int | **业务状态码**（见 §4、§6） | 先判它：200 成功，否则失败 |
| `message` | String | 结果文案；成功多为 `"success"`，失败为可展示提示 | 失败时直接 Toast / 弹窗给用户 |
| `data` | Object / null | 业务数据；分页时为 `PageResult`，加密接口时为密文（见专项文档） | `code==200` 时才有意义 |
| `metadata` | Object / null | 附加元数据（如分页外扩展信息、统计信息），没有则为 `null` | 按需取用；不是所有接口都有 |
| `time` | String | 服务端返回时间，**ISO-8601 UTC**（如 `2026-07-28T09:08:38.123Z`） | 一般忽略；排障时参考 |
| `traceId` | String | 本次请求链路 ID | **反馈问题时务必附带**，后端据此查日志 |

> 说明：当前 SDK 的外层返回对象就是 `ResponseData`；前端只需要把它当成一层统一壳来处理，不要把 `data` 里的字段和外层字段混淆。 |

---

## 4. 成功 / 失败判定

- **成功**：`code == 200`。`data` 为业务数据（分页接口 `data` 是 `PageResult`，见分页文档）。
- **失败**：`code != 200`。`message` 为可展示提示，`data` 一般为 `null`。

**客户端推荐逻辑（伪代码）：**

```text
if HTTP != 200:           // 404 等
    按网络/路径错误处理
else if body.code == 200:
    取 body.data 正常业务处理
else:
    取 body.message 提示用户
    if body.code 属于 5000 段:    // 登录失效类
        跳登录 / 重新登录
```

## 5. 业务 `code` 区间一览

业务码按区间表达不同语义，便于客户端做**分类处理**（如 5000 段统一跳登录）：

| 区间 | 含义 | 典型 code |
| --- | --- | --- |
| `200` | 成功 | `200` |
| `1000–1999` | 系统 / 通用错误 | `1000` 失败、`1001` 参数有误、`1002` 空指针、`1003` 数据库、`1004` Redis、`1005` 访问人数过多、`1006` 重复提交、`1007` 值不匹配 |
| `2000–2999` | 验证码 / 资源 | `2000` 验证码过期、`2001` 验证码错误、`2002` 值已存在、`2003` 值不存在、`2004` 资源不存在 |
| `3000–3999` | 账号 | `3000` 账号已存在、`3001` 账号不存在、`3002` 账号或密码错误、`3003` 账号禁用、`3004` 账号注销、`3005` 手机号格式错误、`3006` 新密码与旧密码相同 |
| `4000–4999` | 安全 / 签名 / 限流 | `4001` 参数签名失败、`4002` 非正常客户端、`4003` 请求频繁、`4004` 最小版本过大、`4005` 已是最新、`4006` 黑名单限流、`4007` 会话密钥无效、`4008` 约定 token 无效 |
| `5000–5999` | 登录 / 鉴权 | `5000` 未提供 token、`5001` token 无效、`5002` token 过期、`5003` 被顶下线、`5004` 被踢下线、`5005` 未登录、`5006` 无角色、`5007` 无权限、`5008` 账号封禁 |
| `6000–6999` | 文件 | `6000` 空文件、`6001` 文件类型错误 |

> 完整的逐条 `code` 含义以 `TechneCode` 常量定义为准；上表为区间速查。新增业务码会保持区间归属，不会突破上表语义。

---

## 6. 排障与 `traceId`

- `time`：服务端 ISO-8601 UTC 时间戳，用于核对时区 / 时序。
- `traceId`：**反馈问题给后端时的必带字段**。把它连同 `code`、`message`、请求参数一起提供，后端可精确定位日志。

---

## 7. 与其他约定的关系

| 你调用的接口类型 | 看哪份文档 | 本外壳是否变化 |
| --- | --- | --- |
| 普通查询 / 列表 | 《分页接口标准出参约定》 | 不变；只是 `data` 变成 `PageResult` |
| 需要参数签名的接口 | 《接口参数签名约定》 | 不变；只是入参要带签名相关头 / 参数 |
| 获取第三方密钥（字段级加密） | 《获取第三方密钥约定》 | 不变；只是 `data` 为密文，需解密 |

**一句话总结：** 不管哪种接口，你拿到的永远是一层 `HTTP 200 + {code, message, data, ...}` 的外壳；分页 / 签名 / 加密只影响 `data` 的内容或入参的附带项，外壳约定始终一致。
