# 获取第三方密钥约定（app / web 调试用）

> 本文档写给 **app / web 调试同学**：说明如何安全地从服务端接口**获取第三方密钥**（如 Google Maps、Stripe、消息推送的 key/secret 等）。
> 整条链路：先拉服务端 RSA 公钥 → 用一次性 AES 会话密钥加密请求 → 服务端返回**逐字段 AES/GCM 加密**的密钥 → 客户端本地解密使用。
> 与 [`分页接口标准出参约定`](分页接口标准出参约定.md)、[`接口参数签名约定`](接口参数签名约定.md) 同属 app / web 联调规范。

---

## 1. 概述

每次请求由客户端（app）生成一个**一次性的 AES 会话密钥**，用服务端 RSA 公钥加密后随请求带上；服务端用 RSA 私钥解出本次 AES 密钥，再用它对请求/响应中的**每个字段**做 AES/GCM 加密。

- **防泄露**：字段在传输中以密文存在，即使被截获也无法还原（密钥不在报文里）。
- **前向安全**：会话密钥每次请求不同，且服务端 RSA 密钥周期性轮换。
- **与签名的关系**：接口签名（见 [`接口参数签名约定`](接口参数签名约定.md)）解决"请求来源可信、防篡改防重放"；本机制解决"敏感字段在传输中以密文存在"。两者可叠加使用，互不冲突。

---

## 2. 服务端 RSA 公钥

app 调用以下端点获取**当前服务端 RSA 公钥**（Base64 字符串），用它加密 `sessionKey` / `token`：

```
GET /api/public/rsa/get-publicKey
→ 响应 data 直接是公钥字符串（Base64），例如 "MIIB..."
```

- **客户端缓存 1 小时**：公钥短时间内不变，避免每次请求都拉取。
- **服务端每 24 小时轮换**一把新密钥，并保留上一把私钥 1 小时宽限。若你遇到 `session key invalid`（4007），通常是服务端已轮换公钥，**重新拉取一次公钥并重试**即可。

---

## 3. 报文结构

### 3.1 请求信封（被标记了会话密钥加密的接口）

```json
{
  "sessionKey": "<RSA 加密的 32 字节 AES 密钥，Base64>",
  "token":      "<RSA 加密的约定字符串，Base64>",
  "payload":   {
    "pageNum":  "<AES/GCM 密文>",
    "keyword":  "<AES/GCM 密文>",
    "profile":  "<AES/GCM 密文（其内部为 JSON 字符串）>"
  }
}
```

- `sessionKey`：你（app）生成的 AES 会话密钥，用**服务端 RSA 公钥**加密（PKCS#1 v1.5），Base64。
- `token`：约定的身份字符串，用**服务端 RSA 公钥**加密，Base64；用于身份校验。
- `payload`：**业务参数字段集合**，每个字段值都是用本次 AES 密钥加密后的密文。

> 注意：这类接口**要求**请求体是上面的信封格式；以明文 JSON 直接请求会因解析失败而报错。

### 3.2 响应（自动加密 `data` 的每一个顶层字段）

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "apiKey":   "<AES/GCM 密文>",
    "secret":   "<AES/GCM 密文>",
    "expireAt": "<AES/GCM 密文>"
  },
  "time": "...", "traceId": "..."
}
```

> 响应里 `code` / `message` 仍为明文；仅 `data` 的**顶层字段**被逐字段加密（List 元素同样逐条加密）。字段名不变，值变为密文，你逐字段解密即可。

---

## 4. 加密算法

### 4.1 服务端如何解出你的会话密钥（黑盒，你只需关心结果）

服务端拿到你请求里的 `sessionKey` / `token` 后，会用 RSA 私钥解出本次 AES 密钥并校验身份。**你作为调用方不需要实现这一步**，只要保证下面两点：

- `sessionKey` 是用**服务端 RSA 公钥**加密的、你本次生成的 32 字节 AES 密钥；
- `token` 是用**服务端 RSA 公钥**加密的、与服务端约定的固定字符串。

服务端内部处理（仅供理解，无需你写代码）：

```
AES 会话密钥 = RSA_私钥解密(sessionKey)        // 解出你生成的 32 字节 AES 密钥
token 原文    = RSA_私钥解密(token)
校验         : token 原文 == 约定字符串 ?        // 不一致 → 4008 token invalid
```

解出的 AES 会话密钥会被用于 §4.2 的字段加解密，且**只在本次请求内有效**。

### 4.2 字段加解密（AES/GCM/NoPadding）—— 你需要实现

- 算法：`AES/GCM/NoPadding`，**128 位认证标签（16 字节）**，IV 随机 **12 字节**。
- **密文格式（与服务端约定一致）**：`Base64( IV(12B) ‖ 密文 ‖ GCM Tag(16B) )`

```
加密: IV = 随机12字节
      cipherText = AES-GCM( IV, 明文, key )
      输出  = Base64( IV ‖ cipherText )          // cipherText 尾部已含 16B 标签

解密: raw   = Base64解码( 密文 )
      IV    = raw[0..12)
      ct    = raw[12..]
      明文  = AES-GCM( IV, ct, key )
```

## 5. 密钥下发接口：这个 API 就是用来获取第三方密钥的

> **这个接口是做什么的**
> `POST /key/get-key-next` 是专门给 app **从服务端安全拉取第三方密钥**的接口
> （如 Google Maps Key、Stripe 公钥、消息推送的 `messageKey` / `messageSecret` 等）。
> 因为这些密钥本身就是敏感凭据，不能明文下发，所以它走的是上面整套加密通道：
> **先拉服务端 RSA 公钥 → 用一次性 AES 会话密钥加密请求 → 服务端返回逐字段 AES/GCM 加密的密钥 → 你本地解密使用**。
>
> 你作为前端 / app 开发，只要记住一件事：**调这个接口，拿回来的是一堆加密字段，用本地 AES 密钥逐字段解密，就得到能直接用的第三方密钥。**

| 项目 | 说明 |
|---|---|
| 接口 | `POST /key/get-key-next` |
| 用途 | 安全获取第三方密钥（Google Maps / Stripe / 消息 key 等） |
| 前置依赖 | 需先调用 `GET /api/public/rsa/get-publicKey` 拿到服务端 RSA 公钥（见 §2） |
| 入参 | 见 §3.1 信封：`sessionKey` / `token` / `payload` |
| 出参 | 见 §3.2：`data` 里每个字段都是加密的第三方密钥 |
| 是否需签名 | 按 [`接口参数签名约定`](接口参数签名约定.md)，若该接口要求签名则三件套照带 |

以「获取 iOS 端第三方密钥」为例，整条流程如下：

- **前置**：先调用 `GET /api/public/rsa/get-publicKey` 获取服务端 RSA 公钥（客户端缓存 1 小时；服务端每 24 小时轮换）。
- **请求体**：`sessionKey` = 你生成的 32 字节 AES 密钥，RSA 加密(Base64)；`token` = 约定字符串 RSA 加密(Base64) 用于身份校验。
- **服务端处理**：1) RSA 私钥解密 `sessionKey` 得到 AES 密钥；2) RSA 私钥解密 `token` 并与约定串比对，不一致返回 `token invalid`；3) 用 AES/GCM 逐字段加密返回。
- **客户端解密**：Base64 解码字段值 → 前 12 字节为 IV，其余为密文(标签附后) → 用本地 AES 密钥 + IV 解密。
- **错误**：
  - `session key invalid`（4007）：RSA 公钥已轮换，重新拉取公钥重试。
  - `token invalid`（4008）：约定 token 校验失败。

返回字段（密文）示例：`apiKey` / `secret` / `messageKey` / `messageSecret` 等，均为 AES/GCM 密文，你按 §4.2 逐字段解密即可得到明文第三方密钥。

## 6. 调用方（app / 前端）参考实现

```java
// 1) 取服务端 RSA 公钥（缓存 1 小时）
String serverPublicKeyBase64 = rest.get("/api/public/rsa/get-publicKey");
RSA rsa = new RSA(null, serverPublicKeyBase64);

// 2) 生成一次性 AES 会话密钥（32 字节）
byte[] aesKey = new byte[32];
new SecureRandom().nextBytes(aesKey);
String sessionKey = rsa.encryptBase64(aesKey, KeyType.PublicKey);          // RSA 加密
String token      = rsa.encryptBase64("app-fixed-token-2026", KeyType.PublicKey);

// 3) 逐字段用 AES/GCM 加密请求参数
String enc(Object v) {
    byte[] iv = new byte[12]; new SecureRandom().nextBytes(iv);
    Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
    c.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(aesKey, "AES"), new GCMParameterSpec(128, iv));
    byte[] ct = c.doFinal(toJson(v).getBytes(UTF_8));
    byte[] out = concat(iv, ct);                                   // ct 尾部含 16B 标签
    return Base64.getEncoder().encodeToString(out);
}

// 4) 组装信封
Map<String,Object> payload = new LinkedHashMap<>();
payload.put("pageNum", enc(1));
payload.put("keyword", enc("techne"));
Map<String,Object> envelope = new LinkedHashMap<>();
envelope.put("sessionKey", sessionKey);
envelope.put("token", token);
envelope.put("payload", payload);
rest.post("/app/user/profile/update", envelope);

// 5) 响应：逐字段解密 data
String dec(String cipherBase64) {
    byte[] raw = Base64.getDecoder().decode(cipherBase64);
    byte[] iv = copyOfRange(raw, 0, 12);
    byte[] ct = copyOfRange(raw, 12, raw.length);
    Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
    c.init(Cipher.DECRYPT_MODE, new SecretKeySpec(aesKey, "AES"), new GCMParameterSpec(128, iv));
    return new String(c.doFinal(ct), UTF_8);
}
```

## 7. 错误码

| code | 含义 | 触发条件 | app 处理建议 |
|---|---|---|---|
| `4007` | `session key invalid` | `sessionKey` 用 RSA 私钥解不开（如服务端已轮换公钥）；或 AES 密钥非法 | **重新拉取公钥并重试** |
| `4008` | `token invalid` | `token` 解密后与约定字符串不一致 | 检查约定 token 是否正确 |

> 错误响应结构同统一响应壳：`{ "code": 4007, "message": "session key invalid", ... }`。

---

## 8. 备注与边界

1. **公钥轮换平滑过渡**：服务端轮换后保留上一把私钥 1 小时，持有旧公钥的客户端在该宽限期内仍能正常请求；你的公钥缓存建议 ≤ 1 小时。遇到 `4007` 优先重试拉公钥。
2. **字段加密范围**：`data` 的**顶层字段**（以及 List 的每个元素）被逐字段加密；嵌套对象会先序列化为 JSON 字符串再加密，你解密后得到 JSON 子对象。
3. **与签名叠加**：本机制与接口签名可同时使用（签名防篡改防重放，本机制防字段明文泄露），二者不冲突。
